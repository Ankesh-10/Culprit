# Phase 5 Plan 02: Near-cap inputs are profiled and every rendered list is bounded

## Phase Goal

ROADMAP Phase 5 goal (verbatim): "Verify the complete vertical slice on the documented rebuild path, fix trust/accessibility/performance gaps, and only then add optional visual polish behind a green-check gate."

MVP note: the ROADMAP goal line is not a user story; no story is invented here (run `/gsd-mvp-phase 5` if wanted).

Provenance: no CONTEXT.md, RESEARCH.md or SPEC for Phase 5; choices are planner discretion grounded in the code.

## Findings this plan fixes (verified in the code)

1. `renderConsidered` in `src/ui/shortlist.ts` renders one table row per entry of `ranking.considered` with no cap. History size is not capped in the core (README "Limitations"), and a chosen history file may be up to 1 MiB, so a few thousand commits become a few thousand rows of DOM. Log lines and the data table are already paged at 100 (`LOG_PAGE_SIZE`, `tableVisible`).
2. `commitMarkers` in `src/ui/timeline-geometry.ts` returns one marker per commit in the domain, and the renderer redraws them on every ResizeObserver tick. With thousands of commits most 8px hollow diamonds overlap at the same pixel and only cost time.
3. No test or browser run has exercised an input at the cap; Phase 4 only asserted the geometry of a synthetic 10,000-bucket timeline.
