## Findings this plan fixes (verified by reading the code, not assumed)

1. The Dockerfile runtime CMD is an inline `node -e` server whose content-type rule only knows `.js` and `.css`. A request for `/` reads `dist/index.html` successfully and then sends it with the generic binary type, so a browser offers the page as a download. The image health check only tests `response.ok`, so it stays green while the demo is broken.
2. The same inline server calls `decodeURIComponent` on the raw path with no guard. A malformed escape (for example `/%E0%A4%A`) throws inside the request callback, which is an uncaught exception that stops the process and the container.
3. The host has `core.autocrlf=true` and the repository has no `.gitattributes`. `git ls-files --eol` shows 28 tracked files already checked out as CRLF, and a fresh clone on any Windows machine would check out every text file, fixtures included, as CRLF. A planning-time probe found the analysis itself CRLF-insensitive (identical canonical-JSON and Markdown hashes for all three fixtures with LF and CRLF input), so this is reproducibility hygiene rather than a known failure: pinning LF makes every clone byte-identical across platforms for every byte-compared file.
4. Docker, make and WSL are absent on this host and the host runs Node 24.14.1, not the pinned 22.20.0, so no Linux rebuild has ever run. A CI workflow is the only automated Linux path available before the deadline.
